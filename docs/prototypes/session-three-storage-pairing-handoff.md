# Session 3 build handoff: protected pairing custody and versioned reads

This increment follows the [Session 2 feasibility decision](session-two-feasibility-handoff.md) for [VLT-03](https://github.com/F2iLLC/lunaos-home/issues/6) and [VLT-05](https://github.com/F2iLLC/lunaos-home/issues/8). It uses fictional records and a Windows-only developer harness. It is not approval for personal information or completion of either issue.

## Decision and result

Keep one authoritative vault host. Pairing, vault unlock, and selected-record grants remain separate decisions. For the Windows synthetic path, a peer certificate fingerprint can now be stored in a purpose-bound CurrentUser DPAPI envelope beside the fixed-example encrypted store. The registry is bound to that store ID and host certificate fingerprint. The direct TLS host loads it before listening, persists new admission before returning pairing success, resumes an enrolled certificate after host restart, and persists device removal. A resumed device receives **no old record grant**. Corruption, a changed host identity, or failed registry writes close or refuse host access; no registry details or OS diagnostics go onto the wire.

The direct TLS experiment can now use the version 2 record contract. In the Windows fixture, a resumed phone reads an authoritative encrypted record with its opaque revision; a stale edit returns `CONFLICT` without overwriting the newer ciphertext. This connects the existing [record revision](../architecture/vault-record-revisions.md) and transport experiments for one synthetic path. The registry is opt-in on the privileged host controller; ordinary Home setup does not yet create or manage it.

## Storage and unlock boundary for VLT-03

The selected Android path still uses Android Keystore/private no-backup storage; the selected Windows path uses CurrentUser DPAPI. The Windows native prompt is an **application access gate**, not an authentication-bound release of the vault encryption key. An ordinary process under the same Windows user may be able to decrypt a copied DPAPI envelope. Neither this registry nor the version 2 fixed `memberId/label/value` record contract supplies production schemas, documents, Sign-ins references, migration, backup, or a configurable unlock method. Do not relabel the gate as key protection.

Before enabling sensitive data: choose and review the production key hierarchy and OS authentication-bound release for the first supported Windows/Android routes; define the supported unlock and method-change rules; choose a versioned record/document format and atomic migration strategy. Prove wrong credential, canceled prompt, OS credential reset, interrupted write, disk-full, tamper, failed migration, restart locked, and no plaintext diagnostic or temporary file. Test clean-device recovery separately under VLT-07. Keep the fixed-example adapter isolated until those checks pass.

## Pairing boundary for VLT-05

The registry stores certificate fingerprints, not vault keys or record values. The existing one-use offer remains short lived and bound to the presented certificate. A real flow still needs installation guidance, host and phone identity confirmation, durable identity/key provisioning, explicit scope review on both devices, visible device management, and a revocation result that distinguishes a confirmed disk commit from an uncertain one. If a registry removal cannot be committed, the running host stops access and returns an error; a later restart must not be presented as safely revoked until the registry has been reconciled. The present harness has no such user-facing reconciliation flow. Re-enrollment after restore, certificate replacement, Android phone-hosted availability, physical reconnect/sleep, and version 2 mutations on an actual paired phone remain open.

### First supported Windows key-release decision

The initial candidate was a device-bound Windows Hello protected asymmetric wrapping key, used only to unwrap a random per-vault data key after a fresh OS-owned gesture. The record file must use authenticated encryption with a separately versioned envelope; no vault key or Windows account secret goes through JavaScript, HTTP, TLS pairing, logs, or a model. The native owner should keep unwrapped key bytes only for a bounded foreground session, clear them on lock/suspend/sign-out/cancel, and restart locked. The same-Windows-user process is in the threat model: CurrentUser DPAPI alone does not resist that process. The existing Windows consent prompt plus DPAPI adapter fails that key-release criterion. Microsoft documents Windows Hello key signing and Passport KSP user gestures, but these sources do not prove this application's wrapping/decryption operation is authentication-bound on the declared device. **No production key-release path is enabled or claimed yet.**

Credential reset or loss of the Hello key must leave ciphertext locked, with no fallback to CurrentUser DPAPI or an old session; recovery requires the separately reviewed user-held VLT-07 backup. Method change must first verify the old method, create and test the new protector, atomically commit a versioned key-envelope change, then retire the old protector only after readback. Cancellation, interruption, full disk, failed migration, or new-method verification failure must preserve the last committed envelope and leave access locked. The family must explicitly approve any added recovery method. Android key release, documents, production schemas, clean-device restore, and independently reviewed security/UX acceptance remain open.

The basis for this decision is Microsoft's [Windows Hello key operations](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello), [Passport KSP gesture behavior](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/rdp-sign-in), and [CNG key creation API](https://learn.microsoft.com/en-us/windows/win32/api/ncrypt/nf-ncrypt-ncryptcreatepersistedkey). These describe platform capabilities, not successful Home key custody.

### Native key-release feasibility result after Session 4

The next native proof was run on the declared Windows 11 Home PC (build 26300). `npm run build:native`, `cargo check --example windows_key_release_probe`, and `cargo test --lib` passed. The disposable Rust probe used Windows CNG directly, with a random 32-byte test key, RSA-OAEP/SHA-256, a persisted key in the named provider, close/reopen, silent decryption in an independent same-user process before and after an attended decrypt. It emits stage labels and an OS status code only; it never prints the test key or an entered password. The probe created no lasting vault files or application access path.

The Microsoft Passport KSP opened but refused an app-created RSA key with `0x80090027` (`NTE_INVALID_PARAMETER`), including an RSA key-exchange attempt. This is a device/provider result; it does not establish that all Windows Hello key creation routes fail. The Microsoft Software KSP accepted `NCRYPT_UI_FORCE_HIGH_PROTECTION_FLAG` and displayed an OS-owned password prompt. An initial same-process close/reopen allowed silent decrypt, so a handle reopen alone is insufficient proof of a fresh gesture. The stricter native probe closed the handle, launched an independent same-user process, and found **silent decryption denied before and after the attended prompt**. Attended decryption recovered the exact random test key. The run ended with `probe-key-removed`. This supports an OS-managed *separate key password* as a first Windows candidate, distinct from the Windows account password and from the existing consent prompt. It does not yet establish production vault-key custody, a configured method, or cold-restart behavior. The password was entered only into the OS dialog; Home did not collect it.

Exact software-provider command: `cargo run --example windows_key_release_probe --quiet -- --attended software`. Its final stage output was `created-protected-key`, `separate-process-silent-decrypt-denied`, `reopened-key`, `attended-decrypt-matched`, `post-prompt-separate-process-silent-decrypt-denied`, `probe-key-removed`, and `probe-result: cryptographic-roundtrip-only`.

The documented Windows Hello user-bound encryption sample uses a [VBS enclave](https://learn.microsoft.com/windows/win32/trusted-execution/vbs-enclaves) and [Microsoft's VBS Enclave SDK](https://github.com/microsoft/VbsEnclaveTooling). On this PC, VBS security service 2 is running and the OS build exceeds the sample's minimum, but the installed Windows SDK is `10.0.26100.0`; Microsoft's current SDK guide calls for `10.0.26100.7463` or later for user binding. The sample also requires an enclave signing path. Do not follow its test setup by disabling Secure Boot or enabling test signing on this personal PC. Pursue that route separately if Windows Hello PIN/biometric unlock is required. The OS-managed separate key password candidate still needs cold restart and locked-state checks, cancellation, wrong password, reset/loss, atomic wrapping-envelope writes, and recovery proofs before it can become a supported method.

The diagnostic source is `src-tauri/examples/windows_key_release_probe.rs`, runnable only with explicit `--attended passport` or `--attended software` arguments. It is a feasibility probe and is not linked to the app's vault service.

## Session 5 local removal reconciliation

The privileged local controller now supports an explicit retry when a removal write has an uncertain receipt. The host still closes access on that failure. The operator must first request registry readback; only a readback showing that exact peer is still enrolled makes a single local retry available. A confirmed retry updates the displayed device state. A second uncertain receipt requires another readback, with no automatic retry or reopened host access. The attended fictional runner asks separately before that retry. This path is not callable through TLS, HTTP, or MCP.

A focused fault test holds a peer in the registry after the first failed removal, checks that retry is denied before readback, then checks an explicitly retried commit and continued host denial. This is controlled-process evidence. The actual phone/PC lifecycle checks, durable identity provisioning, production key release, and sensitive-use acceptance listed above remain open.
