# VersionedVaultRecordStore v2 adapter conformance

Status: draft governing specification for review. It defines what any storage
adapter must do to claim the v2 record-store contract. Passing it is necessary
but not sufficient for production qualification. It does not close #6, #10,
#141 or #151, and it qualifies no adapter by itself.

## Purpose and scope

The [grocery durability matrix](grocery-durability-matrix.md) requires "a
governing conformance specification" before the selected
`WindowsSnapshotFileStore v1` can be qualified, and the matrix must be rerun
against that adapter. This document is that specification for the
**adapter boundary**: the object passed as `store` to
`createVaultSessionService({ store, contractVersion: 2 })` and
`createGroceryPersistence({ store })`. Session grants, disclosure, the grocery
command ledger and UI behaviour are specified elsewhere
([v2 record contract](vault-record-revisions.md),
[grocery command contract](grocery-command-contract.md)).

The key words MUST, MUST NOT and MAY are normative. Every clause below has a
test with the same ID in `test/support/versioned-store-conformance.js`. A test
in `test/versioned-store-conformance.test.js` fails if this table and the
suite list different clauses.

## Adapter surface

An adapter is an object with `contractVersion: 2` and five async methods:

| Method | Success result |
| --- | --- |
| `read(recordId)` | `null`, or `{ revision, data }` |
| `create(recordId, data)` | `{ revision }` |
| `edit(recordId, data, expectedRevision)` | `{ revision }` |
| `editProfile(recordId, data, expectedRevision)` | `{ revision }` |
| `delete(recordId, expectedRevision)` | `{ revision }` (the removed revision) |

`data` is one of the record kinds in `vaultRecordData`
(`lib/vault-record-contract.js`): a bounded profile record
`{ memberId, label, value }`, or a tagged grocery payload
`{ kind: 'grocery-list', list, outcomes }`. Revisions are canonical UUID v4
tokens generated by the adapter. They are change tokens, not permissions or
secrets.

Errors carry meaning only through two classes. `VaultConflictError` means a
definite comparison refusal before any persisted byte changed.
`VaultUnsupportedRecordError` means the target's record kind does not allow
the requested operation, also before any change. Every other failure is
uncertain: callers treat it as "may or may not have committed" and reconcile
by reading, never by blind replay.

## Clauses

| ID | Requirement |
| --- | --- |
| C-01 | The adapter MUST declare `contractVersion: 2` and provide `read`, `create`, `edit`, `editProfile` and `delete`. |
| C-02 | `read` MUST return `null` for an absent record and exactly `{ revision, data }` for a present one, with `revision` a canonical UUID v4. |
| C-03 | `create` MUST require an absent target. An existing target MUST raise `VaultConflictError` and leave the record unchanged. |
| C-04 | `edit` and `editProfile` with the current revision MUST commit and return a fresh revision, including when the data is identical. |
| C-05 | `edit`, `editProfile` and `delete` with a stale revision, or against a missing record, MUST raise `VaultConflictError` and change nothing. The adapter MUST NOT fetch a newer revision to make an old request succeed. |
| C-06 | `delete` with the current revision MUST remove the record and return `{ revision }` equal to the removed revision. |
| C-07 | After delete and recreate, the new record MUST have a fresh revision, and every revision of the old incarnation MUST be refused for `edit` and `delete`. |
| C-08 | Committed records and revisions MUST survive reopening the adapter on the same storage, and a reopened adapter MUST keep enforcing revisions written by any other instance. |
| C-09 | Grocery payloads MUST round-trip exactly through `create` and `edit`, including list items, optional fields and the outcome ledger. |
| C-10 | `editProfile` MUST raise `VaultUnsupportedRecordError` for a non-profile target and MUST refuse non-profile data, without changing the record. Refusing invalid data MUST NOT be reported as a conflict. |
| C-11 | Mutating or refusing a mutation on one record MUST NOT change any other record. |
| C-12 | Concurrent conditional writes from one revision, including from independent adapter instances, MUST commit at most once. A losing writer MAY see a conflict or an uncertain failure, but MUST NOT silently overwrite the winner. |
| C-13 | Malformed record IDs, revisions and payloads MUST be refused before any change, and MUST NOT be reported as conflicts. |
| C-14 | Persisted bytes MUST NOT contain record values or revisions in plaintext. (Applies to adapters with persisted storage.) |
| C-15 | A commit larger than the adapter's ceiling MUST fail without changing state and MUST NOT be reported as a conflict. The Windows probe and the reference adapter use 262144 bytes. |
| C-16 | Values MUST be copied at the boundary: mutating data after passing it to `create` or `edit`, or mutating a `read` result, MUST NOT change stored state. |

## Evidence the suite cannot provide

Some acceptance criteria depend on the adapter's internals and are proven by
adapter-specific evidence recorded in the durability matrix, not by this
suite:

* **Atomic replacement under injected faults.** After a fault before, during
  or after the write, a reopened store MUST hold either the complete old
  record or the complete new one. For the Windows probe this is the fault
  matrix in `test/windows-grocery-persistence.test.js`. A native adapter needs
  its own equivalent.
* **Lost acknowledgement.** A commit whose acknowledgement is lost MUST be
  observable by a later read, and the caller MUST NOT replay it.
* **Physical durability.** Power loss, hard process kill, filesystem variety
  and hostile same-user processes are outside both this suite and the current
  matrix.

## Running it against an adapter

`defineVersionedStoreConformance(test, harness)` registers one test per
clause. The harness supplies `name`, `open()` returning
`{ store, reopen(), dispose() }` over fresh empty storage, optional
`testOptions` for `node:test`, and an optional `atRest(handle)` returning
the persisted bytes for C-14.

It currently runs against:

| Adapter | Where | C-14 |
| --- | --- | --- |
| In-memory reference (`test/support/memory-versioned-store.js`) | every platform | not applicable |
| Windows DPAPI probe v2 (`lib/windows-probe-store.js`) | Windows only, including the hosted `windows-2025` job | applies |

A new adapter claims conformance by adding a harness and passing every clause
on the exact build and platform it claims. Record the commit, OS, runtime and
result alongside the adapter's fault matrix.

```sh
node --test test/versioned-store-conformance.test.js
```
