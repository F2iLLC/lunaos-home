# Home grocery command contract v1

This is a Home-owned, versioned command and receipt contract for the #140 GROC-01 slice. GUI and MCP transports must pass the same `groceryCommand` input to one Home-local command service. Commands select a household and list; those fields do not grant access. The server resolves the target against trusted Home state and executes only inside an existing Home session.

`query` maps to the existing Home session `read` action for the list record. `add`, `edit`, `check`, `uncheck`, and `remove` map to the existing `edit` action and carry the list's expected revision. Item removal remains an edit to the list. This contract introduces no grant, audience, device, session, actor, or permission fields in client input. The session supplies the minimal actor attribution in receipts.

Receipts are typed as `applied`, `queried`, `denied`, `conflict`, or `unknown`. Query content is returned only after a separate selected-content disclosure check. A failed write acknowledgement produces `unknown` with `read-before-retry`; the operation is never automatically replayed. Reusing a request ID with a different command returns a conflict. Identical IDs share one in-process result after each invocation passes the active session boundary. Repeated spoken wording does not imply the same request ID.

The module is a contract/adapter port, not a product route or persistence implementation. Its `withSessionAuthority` adapter must keep the approved Home session active for the whole callback, recheck expiry/revocation at execution time, resolve household/list ownership from trusted state, and set `selectedContentDisclosed` only after approval for the actual grocery fields being returned. The current vault record storage shape cannot hold a full grocery list; this change does not serialize a list into that record or claim a grocery storage integration. #141 owns durable atomic state, durable request-ID outcomes, restart recovery, and fault handling. #142 owns shared GUI/MCP delivery. Until those slices exist, idempotency is process-local and tests use synthetic fixtures only.

No private household data, real device, production service, enterprise runtime, provider connection, grant issuance, deployment, purchase, or rights approval is involved. Labels are not security boundaries, and this contract does not introduce restricted member access.
