## Threat model for the next implementation boundary

The assets are record plaintext, key material, device identities, grants, and the integrity of the authoritative store. Relevant attackers include an unadmitted LAN peer, a previously admitted but revoked device, a local process trying to bypass the Home GUI, an assistant carrying untrusted source text, and a person holding a copied backup or stale ciphertext. A compromised OS account, unlocked admitted device, or malicious authorized user is outside the prototype's protection claim; family members are organizational labels, not security principals.

The enforcing service must authenticate the device before opening a connection, require a live selected-record grant for every operation, bind grants to that connection and expiry, and require separate selected-field approval before data reaches a hosted model. The GUI and assistant adapters must call that same service, never the store directly. The adapter must compare record revisions while holding its commit lock to reject stale edits against the current envelope. That comparison does not detect replacement of the entire store with older valid ciphertext; [anti-rollback protection remains separate work](vault-record-revisions.md) for VLT-03 and VLT-07 storage and recovery design. A revoked or expired grant stops new work; a confirmed write already in flight cannot be undone. An unconfirmed write must not be replayed automatically. Treat document and assistant text as data, never instructions or permission grants. Protect local files and backups with established facilities and avoid record contents in logs, errors, URLs, and CI evidence.

Feasibility evidence supports these boundaries as a design direction, not an end-to-end security claim. VLT-02 owns the shared contract and adapter enforcement; VLT-03/05/07 must close storage, enrollment, and recovery gaps. [VLT-08](https://github.com/F2iLLC/lunaos-home/issues/12) requires independent review and household acceptance before sensitive use.

The original 15–20-session estimate is superseded by the [Session 2 handoff's 18–28 additional focused-session planning range](../prototypes/session-two-feasibility-handoff.md#planning-estimate). That range excludes deferred clients and is not a delivery commitment.
