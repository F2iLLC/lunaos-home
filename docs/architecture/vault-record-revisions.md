# Version 2 fictional record contract

This contract advances [VLT-02](https://github.com/F2iLLC/lunaos-home/issues/5)
through the existing shared authorization service and Windows encrypted probe
adapter. It prevents an approved edit or deletion based on an old read from
overwriting a newer record. It is still a fictional, developer-only experiment.

## Selection and storage boundary

Create a new probe with `openWindowsProbeStore({ create: true, contractVersion: 2 })`
and use `createVaultSessionService({ store, contractVersion: 2 })`. Reopening uses
the same probe ID and version. The service rejects a mismatched adapter version.
The encrypted envelope is format 2, and its DPAPI purpose binds both that version
and the store ID. Each record contains `{ revision, data }` inside the ciphertext.

The default version 1 GUI, MCP, TLS and backup probes remain version 1; they do
not gain revision protection from this change. The Windows native fictional
preview can opt in with `node scripts/windows-vault-native.mjs --contract-v2`
and reopen the resulting store with `--resume-v2 <probe ID>`. Its GUI and
separate stdio MCP assistant bridge use the same version 2 session service and
encrypted adapter. A version 1 adapter cannot open a
version 2 store, and the reverse also fails. There is no silent migration or
fallback to an unconditional write. Version 2 export/import is refused until its
recovery contract is specified. Do not run the old snapshot format against a new
store or infer that a stale revision will remain invalid after restoring an old
ciphertext file. Anti-rollback and clean-device recovery remain separate work.

## Requests and results

Requests use `version: 2`, an opaque `recordId`, and one action. All schemas are
strict. The bounded profile data remains `{ memberId, label, value }`; this is not
a Sign-ins, attachment or arbitrary-document schema. IDs and revisions must not
encode household content.

| Action | Additional input | Storage condition and result |
| --- | --- | --- |
| `read` | None | Returns `{ version: 2, recordId, revision, data }`, or `NOT_FOUND`. |
| `create` | `data` | Target must be absent. Returns a fresh revision. Existing target returns `CONFLICT`. |
| `edit` | `data`, `expectedRevision` | Stored revision must exactly match. Every confirmed edit, even with identical data, produces a fresh revision. |
| `delete` | `expectedRevision` | Stored revision must exactly match. Receipt identifies the removed revision. |

Mutation receipts contain only `{ version: 2, status: 'applied', recordId,
revision, accessEnded }`. Missing targets for conditional edits/deletions are
conflicts. A conflict returns no current revision or record fields. The caller
must obtain an authorized fresh read, review the new state, and explicitly submit
a new change; the service never fetches a newer revision to make an old request
succeed.

Revisions are canonical UUID v4 change tokens generated by the storage adapter.
They survive worker/process reopen. Deletion followed by recreation uses a fresh
token, so an edit or deletion of the old incarnation cannot affect the new one.
They are neither permissions nor secret capabilities. The service copies the
request before queuing so a caller cannot swap the expected revision afterward.

Record, member, and device IDs have explicit bounded, opaque identifier schemas.
The trusted controller assigns and binds a stable device ID to an authenticated
identity; a member designation never serves as identity or permission. The
developer preview uses fixed fictional IDs. Durable enrollment and ID binding
across installations belong to VLT-05, so this process-local admission list is
not a production device registry.

The versioned GUI retains the revision from a confirmed create or read. It
requires a read before an edit when no revision is held and discards a stale
revision after `CONFLICT`. The assistant MCP edit tool requires an explicit
`expectedRevision` from an earlier authorized result; it cannot approve its own
grant or infer a newer value. The GUI and assistant share one store and service,
but have distinct connection-bound grants. An assistant read still needs a
separate selected-field disclosure. The service exposes bounded typed outcomes:
`DENIED`, `DISCLOSURE_REQUIRED`, `INVALID`, `UNSUPPORTED`, `CONFLICT`,
`NOT_FOUND`, `BUSY`, `READ_FAILED`, and `WRITE_UNKNOWN`. Malformed stored reads
become `READ_FAILED` without exposing adapter details.

The privileged controller can inspect the last 128 accepted operation outcomes
in process memory. Each entry contains only a sequence number, opaque device ID,
action, and typed outcome; it has no record values, revisions, grant IDs, or
assistant payloads. It is not a durable audit trail and is not exposed to either
record connection. Persistence and user-facing activity belong to later work.

## Atomic comparison and authorization

The Windows worker validates the requested revision before accessing storage,
then reads and decrypts the envelope under the existing exclusive lock. It checks
existence/revision while still holding that lock and keeps it until the encrypted
replacement is committed. Checking in the Node service alone would leave a race
between independent services; the storage check is required for every adapter.

Only a definite comparison refusal before mutation is a `VaultConflictError` at
the trusted adapter boundary. The service maps that to `CONFLICT`, rechecking
authorization before returning it. The file is unchanged and an otherwise valid
grant remains usable. No record data is attached to the error.

The existing grant rules still apply: admission, selected operation and record,
connection binding, lock/expiry/revocation, and separate assistant disclosure.
Possessing a revision never expands access. An assistant read requires selected
field disclosure and returns only those data fields alongside the revision.
Change-only grants cannot read. Pending reads are checked again before returning
either the revision or content; queued mutations are checked before storage.

## Uncertain writes and contention

Other adapter failures, missing/malformed acknowledgements, or inconsistent
receipt revisions remain `WRITE_UNKNOWN`. The service closes that connection and
rejects its queued work without retrying. A fresh authorized read can show the
committed revision, but durable operation identity and a reconciliation screen
are not implemented. A confirmed in-flight write can complete after revocation;
its receipt reports `accessEnded` rather than claiming rollback.

The Windows worker does not wait for another writer's lock or remove a stale
lock. Lock contention may therefore produce the conservative unknown result
instead of `CONFLICT`; it never reports a second save. Once the lock is available,
a request with the old revision fails the comparison. Crash/power-loss recovery,
hostile same-user filesystem races, Android storage and attended native GUI/MCP
use of this version remain unverified. The automated GUI/MCP contract check uses
an in-memory synthetic adapter; the Windows DPAPI adapter is checked separately.

## Reproduce

```sh
node --test test/vault-record-revisions.test.js
node --test test/windows-record-revisions.test.js
node --test test/windows-preview-v2.test.js
npm test
```

The service tests exercise simultaneous edits, queued edit/delete races, copied
inputs, stale revisions after deletion/recreation, disclosure and expiry, and
committed changes with missing or invalid receipts. Windows-only tests use real
DPAPI files and fresh PowerShell workers to check durable revisions, byte-for-byte
preservation on conflicts, version downgrade refusal, tamper refusal, concurrent
independent services, and a deliberately lost acknowledgement after commit.
The GUI/MCP test exercises one versioned service with separate grants,
disclosure, stale revision refusal, and expiry over the actual local HTTP and
stdio tool adapters.
All records are fictional and the fixtures are removed. Hosted Linux tests skip
the Windows checks; they are not evidence of native device acceptance.
