# Epic: User-controlled shared vault

**Status:** proposed implementation plan; no vault, pairing, authentication, or data protection is implemented by the current starter. This epic implements the vault foundation of [roadmap milestones 1–4](../../ROADMAP.md). Publication is not security acceptance or permission to use real records.

**Tracking:** [User-controlled shared vault epic](https://github.com/F2iLLC/lunaos-home/issues/2). Merging the planning document does not close the implementation epic.

## Product outcome and owner decisions

A household keeps one family vault on its own devices, organized with a **family member designation** on records. Labels such as Mom's vault, Dad's vault, and each child's vault are organizational views of that shared store, not separate security boundaries. Anyone granted access to the family Home system can access all members' records. The family decides whom to admit to that system. A phone-only user can complete setup and use the vault without owning a computer. Onboarding establishes where information lives before asking for records or credentials.

The owner has specified:

- One family vault shared across authorized devices, with member designations for organization. No per-member login, separate access grant, lock, or encryption key is required in this first version. Family access covers every member's information; workflow-specific assistant permissions remain narrower.
- Assistant-guided onboarding asks where to keep information, sets up the vault on a phone for phone-only use, or guides the connection between the phone and computer.
- Private information stays on the user's private devices by default. Home provides no hosted vault, custody, recovery service, cloud synchronization, or image-analysis service.
- Unlocking is configurable: a supported phone passkey/device authentication method, operating-system authentication on the computer, or a separate vault password. These are choices to verify on supported platforms, not universal compatibility claims.
- Optional image-analysis onboarding sends only images the user chooses to their own ChatGPT, Claude, or another selected provider. This is an explicit external disclosure, not local processing. The provider never receives general vault access. The user reviews returned information before saving it locally.
- Users can create, view, edit, and delete their authorized records directly, or delegate record creation, modification, and deletion to their chosen AI assistant. Minimize user effort: the assistant executes authorized operations, rather than merely giving instructions for the user to repeat. Modification includes correcting fields, replacing an attachment, changing categories, and an explicit correction of the family member designation.
- The home screen offers **What would you like to do today?** as an expandable action button. It reveals feature choices, including a proposed **Open my vault** entry. Final feature wording can be refined through nontechnical testing.
- All user-facing language must be understandable without technical knowledge. The account-access category is **Sign-ins**, not “Credentials.” Technical vocabulary remains acceptable in development documentation.

“Local” means the user's explicitly enrolled private devices. Access from a paired phone to a computer-held record necessarily transfers that selected information between those devices over a protected connection; onboarding must say so. It does not mean that a record can appear on another device without a transfer. Granting a human access to the family system includes all member views. Connecting an assistant still requires the workflow permissions the user approves; it does not give that assistant unrestricted read/write authority.

## Starting record types

These are the proposed first catalog and plain-language labels. Templates organize information; they do not imply validation by an issuer, medical advice, or a complete specialist records system.

| User-facing type | Contents and examples | Boundary |
| --- | --- | --- |
| People | Family member profiles: names, contact details, relationships, and links to records. A member selector filters the shared family store. | A designation organizes records; it is not a separate account or privacy boundary. A person admitted to the family system can access every member view. |
| Personal details | Reusable structured records, with initial templates for identification/licensing, insurance, medications/allergies, school details, and provider contacts; allow a user-defined category and fields. | Save reviewed values with their source. A driver's license or professional license belongs here, with its image under Documents and photos, not under Sign-ins. No clinical interpretation or inferred facts. |
| Documents and photos | Selected images, supporting PDFs, forms, cards, and letters, linked to a person and optionally a structured record. | Define supported file types/size limits in implementation; no executable attachments or automatic external analysis. An image and the reviewed details extracted from it are separate linked records. |
| Notes | Private free-text instructions, preferences, and context linked to a person or record. | Treat text as data, not executable instructions. Do not encourage pasting passwords here. |
| Sign-ins | A recognizable service/account entry linked to protected passwords, tokens, or recovery codes where the chosen secure storage supports them; references to device-managed passkeys where supported. | Use established credential storage. Do not imply that passkey private keys can be read, copied, or exported. Showing a secret locally, if implemented, requires explicit local authorization and must never return it to a model. |

Each type must support authorized **create, view, edit, and delete** in the local GUI, with create/update/delete operations also available through the assistant/MCP interface. Both routes call the same service and enforce the same family-access and workflow permission rules. Include category changes, attachment replacement, and deliberate changes to the family member designation. Honor an explicit request or existing scoped delegation without asking the user to repeat approval for every routine operation. Request clarification for an ambiguous target and new authorization for actions outside the grant. Validate required fields, preserve source/review information, and detect stale edits rather than silently overwriting another device's changes. No compulsory secret reveal or copy-to-clipboard feature is implied by viewing a Sign-ins entry.

Changing the member designation is a record edit inside the family vault, not a transfer between isolated vaults. Require an unambiguous target and preserve relationships without losing or misassigning the record. Explain during onboarding that family access includes all members' information. Do not present a person filter as a privacy control. An assistant's approved workflow can still limit which associated records it may use or change.

Deleting a person with linked records must show the impact and require a choice to reassign or delete those records; never silently cascade. Deleting a document must explain any retained reviewed details or references. Deleting a Sign-ins entry must explain whether Home is removing its reference or also removing an item it owns in protected storage; it must not delete an unrelated OS-managed passkey or change the external account. The local activity view records minimal outcomes without preserving deleted record contents.

Calendars, tasks, reminders, and appointment workflows are separate application features; they may link to vault records under their own authorization. Device grants, key material, and recovery configuration are system-managed security state, not editable generic records.

## Plain-language experience

Use familiar labels across navigation, onboarding, empty states, permissions, errors, and help. Explain what happens to the user's information and what they can do next. Technical explanations may be available in development docs or optional details, but must not be necessary to complete a routine task.

| Development concept | User-facing wording or explanation |
| --- | --- |
| Credential / secret reference | Sign-in; “Your password stays protected on your device.” |
| Authoritative vault host | “Where your information is kept” and “This device needs to be available.” |
| Device enrollment / pairing | “Connect your phone and computer.” |
| Authentication | “Unlock” or “Confirm it's you.” |
| Authorization / revocation | “What this device can access” / “Remove access.” |
| Provenance / extraction review | “Where this came from” / “Check these details.” |
| Concurrency conflict | “This record changed on another device. Review both versions before saving.” |

Do not replace precision with reassurance: for example, clearly say that sending a selected image to the user's AI provider takes it outside their devices. Do not label something “safe,” “connected,” or “saved” without the evidence that supports that state. The nontechnical acceptance test must show that users can distinguish Sign-ins from licenses, choose where information lives, understand the selected-image disclosure, and recover from an error without knowing MCP, cryptography, or networking terms.

## Workflow plugin, Home interface, and local data

The product consists of three connected parts: workflows offered through the user's existing ChatGPT/Claude, the Home GUI for viewing/reviewing/managing records, and the data structure plus enforcing service on the user's personal device. Use “plugin” in product discussion where appropriate; MCP is the tool connection, not the workflow itself or a universal installation format. The workflow recommends permissions and guides the task; the device-local service enforces grants and performs operations. Instructions in an assistant prompt are not an access-control mechanism.

Reuse the same Home interface when launched from the assistant or opened directly. Verify whether each supported client can embed that interface or must open it locally; preserve the intended member/record/task context without passing secrets in links. Do not promise that a provider-hosted frame can display private data while keeping it device-local without measuring its data path. A private local window is the fallback when embedding cannot satisfy the custody boundary.

## Recommended workflow permissions

Every workflow specification must state its purpose, recommended operations, associated records, any provider disclosure, duration, approval step, and completion/revocation behavior. Suggestions are not grants: the user explicitly accepts them. Human family-system access covers all member records; these workflow limits govern the assistant, not privacy between family members.

| Workflow | Recommended permission | User decision and end condition |
| --- | --- | --- |
| Initial vault setup | Create the family vault, member designations, and selected records; read/review and modify records needed for setup. No deletion or standing write authority by default. | Ask whether the user wants help and authorizes setup. A yes grants create/edit only for this local setup session. End the grant on completion, cancellation, lock, explicit revocation, or expiry. |
| Identification intake | During the approved setup session, add/edit selected identification records and their member designation; review extracted fields before commit. | Each document type is optional. Any selected-image analysis needs its provider disclosure/selection; setup permission alone does not authorize upload. |
| Executive-assistant form preparation | Read only the associated records/fields needed to populate the requested form. No edits/deletions to source records. | Recommend and explicitly approve this access during onboarding. If values must go to a hosted assistant, include those fields and destination in that approval. State the approved duration; no implicit permanent grant. Produce a reviewed draft, without external submission. |
| Learn about me | Use the assistant's available memories and read relevant information from already connected/authorized sources such as Gmail and calendars; create a draft profile in the Luna OS GUI. No sending, source edits, new connections, or automatic vault writes. | Invoke the skill or enable it during onboarding and explain the sources it will use. Work autonomously within that task's existing authorized scope without per-item prompts. Review the on-screen draft with the user; saving requires the active setup write session or a separately approved save operation. |
| Later record creation or editing | Create/update the selected records or categories for the requested task, with necessary reads. | Use an existing applicable grant or approve a bounded task/session grant. Do not inherit expired onboarding write access. |
| Record deletion | Delete the unambiguously selected record(s); no automatic delete permission from read, setup, or edit grants. | The user's explicit deletion request can authorize that bounded action. Clarify ambiguity; respect an existing approved delete scope without repetitive confirmation. |
| Connect a computer | Perform supported bridge installation/configuration and verify the connection on authorized devices. No automatic record disclosure to the model. | Obtain setup authority, automate supported steps, and ask the user only for required OS interactions/device identity approval. Pairing alone grants the assistant no unlimited record access. |

Bind session-only permissions to a service-enforced local workflow session, not merely the continued existence of a hosted chat. Specify maximum lifetime/inactivity rules in the implementation decision record; deny on expiry and after process restart until a fresh session is authorized. Check validity when queued work executes. Show “You can make changes during this setup” and “Setup finished—permission to make changes has ended.” A new chat or reconnect cannot resurrect a previous grant.

## Delegation with minimal user effort

Manual controls and assistant delegation are equal supported paths. A user can ask their own ChatGPT or Claude to add, change, or delete records. For example, after selecting a fictional note locally, “Delete this note” should execute that specific authorized deletion and report the observed outcome; it should not become a tutorial requiring the user to repeat the operation in the GUI.

Set up a revocable grant for the selected assistant/client, family system, workflow, associated record types or records, operations, and duration. Create, edit, delete, and disclosure/read authority are separate permissions. A grant covers routine requests only within its approved scope and duration; no mandatory confirmation per record is imposed. Onboarding setup writes are session-only, never a persistent grant by default. The user can inspect/change/remove it locally. Deleting an entire vault, changing security/recovery settings, granting access to someone else, and changes outside the workflow's selected records are not implied by ordinary record-management authority.

Keep data local by separating **permission to act** from **permission to disclose content to a hosted model**. The local app can supply short-lived scoped record handles or staged changes so an assistant can request an operation without receiving a record's private contents. Handles must be checked against the caller's grant and vault; possession alone is not authorization. Return a minimal accurate completion/conflict/denial result, with private details visible locally. Never return passwords, recovery material, or vault keys.

If the user types private values into their chosen hosted assistant, those values have already been disclosed to that provider; do not describe that conversation as device-only processing. If a delegated task needs Home to send existing private fields to the model, explain the selected fields, destination, and purpose and obtain scoped disclosure permission first. This may be an explicit grant for the task rather than repeated prompts for each field; absent permission, execute through local references/staged values or ask for the missing choice. Blanket vault access is never implied by delegation.

Assistant-proposed changes must pass the same validation, family-access and workflow checks, record-version checks, and safe retry rules as manual changes. Prompt text in documents or returned analysis cannot grant permissions. Recheck authorization at execution; lock/revocation stops queued and subsequent work. Show what changed and whether it actually saved, with minimal local activity evidence. Define undo/recovery availability honestly, rather than promising every deletion can be reversed.

For selected-image analysis, a verified assistant/MCP route may return proposed structured results directly into local review, avoiding manual retyping or copying. The selected-image disclosure and review requirement still apply; a proposal is not a committed record until the review decision is supplied. Manual handoff remains a fallback, not the only target experience. Purely routine, already-authorized record changes do not inherit this extraction-specific review gate.

## Vault UX flow

This is a proposed UX flow, not a working screen. The welcome screen/checklist remains the only implemented interface.

1. **Offer help when useful.** Based on the user's stated needs, the assistant suggests a family vault and asks, “Would you like me to help you set up your family vault?” Do not scan personal data to decide relevance. Decline skips setup; the home feature remains available later.
2. **Approve the setup session.** Explain where information stays, that family-system access includes all members, and the recommended create/edit permission for this setup only. Ask, “May I create and organize records during this setup?” Decline grants no write access. Show the current setup permission and how to stop it.
3. **Choose where information lives.** Phone directly, or computer. For computer storage, guide the user to their own ChatGPT/Claude on that computer and connect the local Home service/bridge. Automate supported installation/configuration steps under the approved scope; retain only necessary user OS/security interactions. Unsupported client/device combinations remain incomplete, with an explained alternative rather than a fabricated success.
4. **Choose unlocking and verify access.** Set up a supported device/passkey or vault-password option and user-held recovery. Approve the device connection when applicable. Test the actual local vault/bridge before claiming it is ready.
5. **Start from what the assistant can learn, or enter details yourself.** Offer **Learn about me**, or reuse a reviewed output from that skill, to propose the user's profile and family member designations. Review/correct the suggestions together, then save approved details under the setup session. Manual entry and skipping remain available. Choose a member and ask which records to organize first; no category is mandatory. Member views organize shared family information, not private compartments.
6. **Offer identification types one at a time.** Ask whether the user wants to store identification or use it to fill in personal details. Offer birth certificate, Social Security card, driver's license, state-issued ID, passport, permanent resident card, and work ID, plus another type. Tailor the list to the user's context and make every choice skippable. No document is required to establish family-system access.
7. **Choose how to add it.** Manual details, selected file/photo stored locally, or optional analysis through the user's chosen provider. Separately ask whether to keep the original image, the reviewed details, or both. Explain exactly which image leaves the device if analysis is chosen. Never upload skipped or unselected documents. The assistant can submit proposed results directly for local review, avoiding retyping.
8. **Check and save.** Show the proposed details, source, and family member. Correct uncertain values and confirm the extraction result; do not infer missing identity values. The assistant saves through the local service under the session grant, reports the observed result, and offers another item or “Finish for now.” Manual controls remain available throughout.
9. **Offer useful ongoing workflows.** For example, “Would you like your assistant to use these details to prepare forms?” Recommend read-only access to associated records, disclose any model-bound fields, and obtain explicit approval with its own duration. Declining keeps the records usable manually and grants no workflow access.
10. **Finish and return home.** End setup create/edit permission, summarize what was saved and where, and show the next action. From home, **What would you like to do today?** expands features including the proposed **Open my vault** entry; a family member selector filters the shared records. Later delegated changes use their own applicable grant.

At every step, cancel/skip/back must preserve confirmed work, avoid silent duplicate saves, and make uncommitted drafts clear. Interrupted setup must distinguish a saved vault/record from an unfinished bridge or draft; resuming requires a valid setup session rather than extending old write authority automatically. Use synthetic identification examples in all design and acceptance evidence.

## Plugin skill: Learn about me

**Purpose:** reduce setup effort by using what the user's own assistant can already access to propose a preliminary personal and household profile. Its output is an input to vault onboarding, not an independently verified identity record.

**Source pool:** include memories actually available to the user's assistant, plus already connected and authorized sources such as Gmail and calendars. The host assistant can use memories available in its context when forming the draft; Home does not need to copy the assistant's complete memory store. Verify whether each client exposes relevant remembered context or a supported memory capability; never assume a plugin can enumerate all ChatGPT/Claude memories or read internal memory files. Mark unavailable sources honestly, and continue with the sources that work. Record remembered statements as assistant-memory evidence with known date/uncertainty, not automatically as verified facts or equivalent to a current document.

**Trigger and access:** when the user invokes the skill or enables it during onboarding, identify the sources actually available to that assistant and briefly explain the read-only task. Reuse existing authorized access to email, calendars, and other relevant connected sources; do not require a fresh prompt for every message or event. The skill does not connect new accounts, ask for account passwords, extend access beyond existing grants, or treat inaccessible sources as available. A source becoming available later does not silently expand an in-progress agreed search. Do not read local folders solely because a remote assistant can see an email attachment link.

**Autonomous work:** choose relevant searches, inspect context, and combine evidence into candidate details and family relationships. Use bounded searches and source limits appropriate to the task, recording coverage and gaps rather than claiming to have read everything. Continue with available sources when one is unavailable; explain the limitation. Read-only means no email sending, draft sending, calendar changes, contact updates, invitations, or other external side effects. Embedded instructions in emails/events/attachments are source material, never commands or permission grants.

**Draft output contract:** include candidate user profile, proposed family member designations/relationships, proposed profile fields, and items needing clarification. For each candidate, include a concise source reference, observation date/freshness, whether it is directly stated or inferred, and uncertainty/conflicting evidence. Use the minimum supporting excerpt needed for review; do not import entire mailboxes, calendars, or unrelated messages into the vault. Group duplicate mentions conservatively and retain unresolved identity matches as questions. A frequent contact, shared surname, emergency contact, coworker, or event attendee is not automatically a family member. Do not guess government identifiers or infer diagnoses or other sensitive personal traits as profile facts.

**Review together in the Luna OS GUI:** the assistant submits the structured proposal to a local draft-review operation and opens the same Home interface, embedded only where verified safe or in a local window. Show the proposed personal profile and family members on screen, including plain-language source labels such as “Remembered by your assistant,” “From Gmail,” or “From your calendar,” and visible uncertainty/conflicts. The user can confirm, correct, remove, or skip details and people while discussing the draft with the assistant; no manual copying of the entire profile is required. Draft display is distinct from committing records. The review operation accepts only a bounded proposal and cannot mutate the saved vault; any retained draft must use encrypted local storage, be labeled unconfirmed, and have a discard path. Clearly distinguish “suggested” from “confirmed by you”; confirmation is not issuer verification. Resolve ambiguous family membership before adding the designation. Save only approved fields/person assignments under an active setup create/edit grant or an explicit later save grant. If no write grant is active, keep the result a draft; a read-only skill invocation cannot create lasting vault write permission. On repeat runs, propose differences and never overwrite user corrections automatically.

**Field-level correction:** every assistant-filled field is selectable by touch/keyboard and can be marked **Needs review**. Route its draft/field identity and permitted context to the current assistant workflow so it asks, “What needs to be changed?” Apply the user's correction to the draft, show the revised value, and request confirmation of that correction without redoing the entire profile. Do not silently send undisclosed field contents to a hosted model merely because it was selected. Pending/unclear corrections remain flagged; save reviewed fields only and clearly identify skipped/pending ones. If the assistant is disconnected, keep the flag and offer manual editing. Test repeated selections, conflicting corrections, an expired setup grant, and persistence of user corrections on re-analysis.

**Suggest useful records:** use reviewed discoveries about applications/services, work, library membership, or other relevant context to ask whether the user wants to store associated information for that family member. For example, suggest an employment record or library-card record, with the source and uncertainty shown. Discovery does not authorize creating every suggested record, connecting an account, or guessing an identifier. Accept, decline, or defer each category; reuse approved known details to minimize typing and ask only for missing details. Store chosen, reviewed records under the active grant and correct member designation. Do not repeatedly prompt for a declined suggestion in the same workflow.

**Custody:** email/calendar originals remain with their existing providers. The chosen assistant processes source information under its provider's terms; this step is not device-only analysis. Home operates no profiling backend and acquires no source-account credentials. Store only the reviewed profile output locally in the encrypted family vault. Avoid returning existing private vault contents to the hosted assistant without the separately approved disclosure scope. Labels, permissions, progress, and errors remain plain language.

**Failure and acceptance:** test with fictional assistant-memory and email/calendar fixtures containing a coworker with the same surname, ambiguous attendees, old addresses, duplicate contacts, conflicting relationships, and misleading embedded instructions. Verify the skill creates a reviewable draft, clearly identifies uncertainty and unavailable sources, sends/modifies nothing externally, and commits no unreviewed profile. Confirm that a session expiring during review blocks a later save, revoked source access stops further reads, corrections survive repeat runs, and users without connected sources can continue manual setup. Verify the source tools and presentation supported by each declared ChatGPT/Claude environment before promising compatibility.

## Proposed architecture and bounded scope

For the first implementation, propose **one authoritative host for the family vault** with authenticated direct access from a paired device. The host can be the phone or computer; phone-only mode runs the same service locally. This avoids a second writable replica and conflict-resolution engine in the first slice. Confirm the hosting/transport choices in the platform spike, especially mobile suspension and background limits. Do not silently substitute a desktop requirement for phone-only support.

Start with a verified same-network or direct local connection. Internet relay services, public vault endpoints, automatic port forwarding, remote access from anywhere, unattended multi-device synchronization, offline replicas, and automatic failover are outside this epic. If the host is asleep, offline, locked, or disconnected, show the correct unavailable/locked state; do not imply a successful save or retain an undisclosed plaintext cache. If remote or offline access later becomes necessary, plan it explicitly with its custody and consistency consequences.

One shared VaultService enforces actor, enrolled device, vault, person, record, action, and authorization scope on every operation. GUI and MCP are adapters to that service, not separate policy engines. Authenticated family-system access covers all member views for a human user. An assistant additionally needs an approved workflow grant for its reads and mutations. Network presence, knowledge of a path, a household profile, and a pairing code alone do not grant permanent access.

| Component | Required boundary |
| --- | --- |
| Local vault storage | Encrypt records, documents, and sensitive metadata; use a reviewed maintained storage/encryption facility. Stable opaque IDs must not reveal person names in filenames. Atomic writes, versioned schema, integrity checks, and migrations preserve recoverability. |
| Key and credential adapter | Use established platform facilities and reviewed libraries. Keep vault keys separate from encrypted data. Reusable integration secrets use protected credential storage and scoped references; no raw secret appears in model output. |
| Local GUI | Own storage selection, unlock, pairing approval, access management, private records, import review, recovery, and meaningful error presentation. OS authentication remains in the OS prompt. |
| Paired-device connection | Mutual authentication, encrypted transport using a maintained protocol, bounded permissions, replay protection, expiry, disconnect, and revocation. A local network is not trusted merely because it is local. |
| Assistant/MCP adapter | Guide setup and invoke authorized local operations. Return minimal non-sensitive status by default; keep private names, paths, document contents, and profile values out of hosted model context unless covered by explicit selected-content disclosure permission. Keys and authentication secrets never enter model context. Private on-screen results are not automatically tool responses. |
| Local activity view | Distinguish configured, verified, attempted, and observed outcomes with freshness. Keep minimal audit evidence locally without record contents or credentials. Home cannot observe unrelated assistant actions. |

Storage selection must consider OS/cloud backups, synchronized folders, temporary files, previews, clipboard, notification contents, crash reports, and logs. No Home telemetry or hidden upload. Explain any platform limitation and prevent unsupported storage configurations from being presented as verified local-only storage. Do not claim protection against a compromised OS or an attacker already controlling an unlocked authorized device.

## Configurable unlocking and recovery

Unlock choices must actually control access to protected key material, not merely dismiss an app screen. Startup is locked. Manual lock is always available; configure inactivity and lock-on-suspend policies without silently disabling protection. Changing or removing an unlock method requires local reauthentication, a verified replacement/recovery path, and a transactional update that cannot strand the vault.

| User choice | Implementation investigation and acceptance |
| --- | --- |
| Use phone security / a passkey | Verify a device-bound method and its key-release mechanism on the chosen mobile target. Ordinary passkey authentication is not automatically an encryption key. Check whether the selected credential/provider synchronizes secrets off-device; do not offer an unverified synced credential as device-only protection. Show only tested options. |
| Use computer security | Use supported OS authentication and protected key storage. Never ask Home or the assistant to collect, store, or reuse the Windows account password. Verify the actual supported OS prompt and fallback; do not relabel a Windows Hello PIN as the Windows password. |
| Set a vault password | Use a maintained password-based key-protection facility with a unique salt and reviewed resource parameters; never use the password directly as an encryption key or invent a cryptosystem. Verify wrong-password behavior, password changes, and resistance to offline guessing. Local retry controls alone do not protect a copied encrypted vault. |

Authentication and vault-key recovery are separate. Losing the device, resetting OS authentication, losing a passkey, or forgetting a vault password must have a documented outcome. Offer a reviewed user-held encrypted backup/recovery method on user-controlled local media; no operator escrow or cloud reset. Explain that without a working recovery path some loss is irrecoverable. Backup creation alone is not recovery evidence: demonstrate restoration on a clean supported device with synthetic records. Device-bound integration credentials may require re-entry; never promise they are portable.

These are design requirements. [Microsoft's Windows Hello documentation](https://learn.microsoft.com/en-us/windows/apps/develop/security/windows-hello) describes device-specific authentication and protected key operations; it does not by itself select a vault-encryption design. [The W3C WebAuthn PRF explainer](https://github.com/w3c/webauthn/blob/main/explainers/prf-extension.md) describes an additional capability relevant to deriving key material; availability must be tested on the actual client/authenticator. [OWASP's cryptographic storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html) informs threat modeling and key separation. No library or platform is approved by citation alone.

## Selected image analysis without Home custody

This optional path is an explicit selected-content exception to keeping record content on private devices. Use the user's own chosen assistant/provider; do not introduce a Home analysis backend or assume a subscription supplies an API key.

1. The user chooses a specific image and destination. Explain that it will leave their devices and be handled under that provider's policies. Never promise zero retention or that deleting Home's local copy deletes provider history.
2. The user attaches the selected image in their own provider app, or uses a verified selected-image handoff they explicitly authorize. Home can give generic instructions and a structured field template, without embedding private data in that template. Do not claim an upload occurred or analysis succeeded unless actually observed; manual handoff remains labeled user-reported.
3. The assistant can submit proposed structured results through a verified scoped MCP operation for local review; manual return remains available when unsupported. Verify and restrict the return integration; provider responses are untrusted input, not instructions or authorization.
4. Show proposed values, source, uncertainty/missing fields, and intended household member. Let the user edit/reassign them, then save only after explicit local review. No automatic overwriting, guessing, or cross-person assignment.
5. Decline, cancel, provider failure, and partial results all leave manual entry available. No general filesystem access, vault-wide grant, background extraction, or analysis API billed by Home is required.

Consent for one image is not permission for further images, vault browsing, sending credentials, calendar writes, or external commitments. A private-data tool response or other export needs its own purpose/destination/scope decision as described in the delegation contract; it is not implicitly approved by pairing or general assistant setup.

## Acceptance journeys and failure matrix

**Delegate or do it yourself:** from the expanding home menu open a family member view, manage a synthetic record directly, then grant a supported assistant permission to create, edit, and delete selected records in the family vault. Complete those operations conversationally without repeating them in the GUI or reconfirming an in-scope request. Verify saved state locally, verify that an admitted human can view both members while an assistant is denied records outside its workflow grant, clarify an ambiguous deletion, exercise a stale edit/retry, and revoke access while work is queued. Demonstrate both opaque local references without private disclosure and an explicit selected-field disclosure grant. Record the number of user steps and remove unnecessary re-entry/confirmation while retaining required choices and accurate results.

**Phone only:** after installation, with no computer and no internet, launch the supported local app, choose phone storage and unlocking, create two fictional member profiles in the shared store, save a reviewed synthetic record, lock, restart, unlock, and recover it. Optional hosted image analysis requires internet and remains a distinct opt-in; its absence must not block manual onboarding.

**Phone and computer:** for the family vault, choose the authoritative device, enroll the other with confirmation on both, save a synthetic record on one interface and verify its committed version through the other. Test both supported host directions. A sleeping or suspended phone host must be shown unavailable where the platform cannot maintain service. Revoke the paired device and verify that subsequent operations, queued requests, and reconnections are denied. Repeat setup with a declined pairing request; no device is enrolled.

| Risk / failure | Required evidence |
| --- | --- |
| Undisclosed external disclosure | With synthetic canary content, inspect Home traffic, model/tool payloads, logs, caches, backups, and diagnostics. With analysis and selected-field disclosure declined there is no record egress beyond explicitly enrolled devices. Delegated local operations still work without returning private content. With selected analysis or field disclosure, only the explicitly selected content goes to the authorized provider; any manual provider action is distinguished from Home-observed traffic. |
| Wrong designation or excessive assistant permission | An admitted family user can access both fictional member views; filtering is not a security boundary. An unadmitted client is denied the family system. Assistant reads/writes are restricted to approved workflow operations and associated records. Correcting a designation edits the record without creating a new access boundary. |
| Secret leakage or weak unlock gate | No raw credential, key, or recovery material appears in model results, logs, plaintext persistence, or pairing payloads. Private fields appear in model results only under an explicit scoped disclosure grant, never incidentally in status/errors. Canceled/failed OS authentication denies access. An app-screen bypass cannot decrypt data. |
| Network attack or duplicate operation | Mutual identity checks, encrypted connection, replay rejection, timeouts, idempotent mutation IDs, and version conflicts are exercised with a synthetic hostile peer. A timeout is an unknown outcome until reconciled, not permission to blindly repeat a write. |
| Lock, revoke, or device loss | Check authorization again when work executes; stop queued/new access and close sessions. Document any completed/in-flight disclosure that cannot be recalled. Pairing grants and sensitive caches do not resurrect after reinstall or restore. |
| Crash, corruption, or lost credentials | Interrupted write/migration, full disk, bad recovery key, malformed backup, and unsupported version fail without silently replacing recoverable data. Successful restore is verified, not inferred from archive creation. |
| Local document attack | Enforce types/size limits and reviewed preview/parsing boundaries. Embedded scripts, external resources, and prompt instructions cannot execute or expand permissions. Preserve originals; explain copies rather than claiming secure deletion from all storage. |

Deletion removes the selected active record and its indexes/references under the documented retention policy; existing user-held backups and original source images are separate copies. Do not promise remote wiping, forensic erasure on SSDs, or protection from an already compromised authorized endpoint.

## Gates, open decisions, and exclusions

The owner has decided one family vault organized by member designation and shared across authorized devices, phone-only operation, onboarding-led location choice, configurable unlocking, local custody, direct or delegated record management with minimal user effort, an expanding home action menu, optional user-provider image analysis, and Android as the first mobile target. Remaining engineering decisions are the test device/OS version, packaging/runtime, established storage/key library, supported unlock methods and recovery mechanism, direct transport, and safe mobile host availability. Present measured tradeoffs at VLT-01; never silently relax the local custody boundary to make a client work.

Deferred: cloud/relay hosting, remote access from anywhere, offline multiwriter sync, public unauthenticated endpoints, operator recovery, unattended third-party uploads, a Home analysis/model/voice service, general password-manager features, remote wipe, automatic migration between authoritative hosts, and per-member privacy boundaries and full multi-user household identity administration. A safe reviewed export/restore can support an explicit move later; do not create two competing authoritative hosts accidentally.

Read/write calendar integration and appointment workflows remain separate roadmap work. This vault epic does not grant blanket authority to send private profile fields to them or to hosted models. Each external action retains its own destination, content, and scope boundary.

Apply [repository rules](../../REPOSITORY_RULES.md) and [collaborator responsibilities](../../COLLABORATORS.md). Use original or expressly authorized dependencies/material only. Public repository Actions uses the reviewed standard GitHub-hosted workflow, with Home excluded from organization, enterprise and repository-level self-hosted runners. The synthetic fork routing checks passed; the [CI handoff](../ci-actions-setup.md) tracks remaining acceptance evidence. Real household data, credentials, screenshots, private device paths, and logs never belong in source, issues, PRs, or CI evidence. A second-person sensitive-design review and owner acceptance remain human gates; publishing this plan does not complete them.
