# Proposed V1 roadmap

This is product scope for discussion and implementation, not an implementation report, release promise, or dated schedule. Today the dusk welcome screen and session-only checklist work. The [repository rules](REPOSITORY_RULES.md) govern all milestones, and [COLLABORATORS.md](COLLABORATORS.md) assigns decision ownership. The [user-controlled shared vault epic](docs/epics/user-controlled-vault.md) expands milestones 1–4 into delivery stories and acceptance criteria.

## V1 goal

An ordinary household user can use an existing AI subscription plus a local Home GUI on mobile and desktop to prepare for one appointment and follow through on its requirements. They can see relevant household calendars, use reviewed information from the correct person's local profile, understand what Home can access and do, and review useful results without having to understand MCP internals. The starting experience should feel simple and restful, with a dusk palette and clear touch/keyboard navigation.

The GUI and MCP interfaces share local services, authorization, and state. The user's own Claude or ChatGPT hosts conversation/voice; Home supplies tools, onboarding scripts, and workflows. Home shows its own observed activity, not a supposed complete view of the assistant or unrelated connectors.

## Scope and proposed first combination

Propose Windows 11, one verified Claude desktop client/version, and Google Calendar as the first desktop development combination. Mobile app support is also required: select and verify an initial mobile platform/client and delivery approach in milestone 1 rather than assuming desktop MCP or filesystem access works on a phone. A responsive browser layout alone does not complete installable app delivery. These are candidates to validate, not current compatibility claims or installed integrations. Verify optional selected-image analysis in the user's own chosen ChatGPT, Claude, or other provider, with a verified assistant-to-local-review return path and manual handoff as a fallback. Home does not provide an analysis service or require its own analysis API integration. Record the exact client, plan, platform, permissions, processing terms, and any user-provider charges before offering that path; do not assume a subscription includes API access.

Evaluate ChatGPT and voice/tool operation explicitly, but expand the support matrix only when tested. If a proposed combination cannot reach local MCP or perform the required workflow safely, select a verified alternative with the owner before committing to it. Do not expose a local vault to the public internet as an implicit workaround. Unsupported voice combinations must be labeled; offer text plus on-screen review rather than claim voice support. The owner must accept the supported V1 experience at the compatibility gate.

| In V1 | Outside V1 / later |
| --- | --- |
| Scoped local discovery, GUI access/activity/results views, and Home MCP tools over shared local services | Arbitrary filesystem scans; a separate GUI engine; full visibility into external assistant activity |
| One family vault on user devices, organized by member designation: phone-only operation or explicitly paired phone/computer access, direct or assistant-delegated record changes, configurable supported unlocking, and user-held recovery | Operator-hosted vault, operator custody, cloud backup/sync, offline multiwriter replicas, a new password manager or custom cryptography |
| Selected document-photo intake, optional analysis in the user's chosen provider, local review/correction, and person assignment before save | A Home analysis service; broad vault disclosure to hosted models; bulk unreviewed imports; silent guessing; local-model analysis in the first release |
| Needs-led onboarding and purposeful MCP choices in a verified assistant environment | A new Home voice service, central third-party connector control, universal client/voice/MCP promises |
| Read/write unified calendar for multiple people/accounts from one verified provider: view, create, update, and delete events on authorized calendars, with person/source filters | Every calendar service, attendee invitations/notifications, or cross-provider conflict resolution |
| Appointment preparation, reviewed local form drafts, manual recording of confirmation, local follow-through/reminders | Autonomous booking, external form submission, sending messages, payments, or unattended external commitments |

V1 calendar writes must use scoped authorization, visible intent/results, and a local audit trail; already-authorized routine actions should not require repeated prompts. Show the target person/account/calendar and the proposed change, including whether a recurring-event change affects one occurrence or the series. Creating a calendar entry does not book an appointment with a provider. Optional image analysis is an explicit selected-content disclosure to the user's chosen provider, not permission for general vault access, further exports, booking, or submission. Private vault values remain local by default; separately disclose and authorize any private content included in an external action. Attendee invitations/notifications remain outside V1; do not perform a calendar write if the provider cannot avoid those external messaging effects.

## Architecture and reuse

Use one local application service layer for discovery, permissions, vault/profile operations, calendar normalization, and workflow state. The GUI and Home-owned MCP tools call those same services, so policy and state cannot diverge. Keep an explicit representation of configured access, verified access with a timestamp, attempted actions, and observed results/errors. Display origins and freshness, and mark external activity unknown when Home cannot observe it. Discovery starts from locations/configuration the user chooses; seeing a path is not permission to read it.

Evaluate suitable enterprise LunaOS contracts, libraries, and skill/tool/workflow machinery before rebuilding the same capability. Reuse only through deliberately versioned interfaces after written rights authorization and license review. Enterprise LunaOS is proprietary, and its workspace packages have substantial product dependencies; they are not independently consumable Home packages today. No enterprise code is copied or extracted by this plan. Do not bring over the full enterprise runtime or build a Home voice service just to reuse code.

Home needs separate configuration, credentials, data/vault, logs, sessions, event/tool names, and background-job identity. Before reuse, examine configuration/environment discovery, inherited child-process environments, relative transcript/knowledge/memory paths, scheduler queues, and worker namespaces. Existing collision checks and tool prefixes do not prove data or security isolation. Test operation beside an enterprise configuration without loading it or altering it. Shared code must not force public contributors to access private enterprise repositories.

## Sequential milestones

### 1. Verify a useful supported combination

**Outcome:** a user sees an honest setup path and knows which features their existing assistant environment supports.

**Depends on:** owner acceptance of the proposed V1 boundaries; rights review before selecting shared components; access to test accounts/client versions without collecting household records.

**Acceptance:** demonstrate one harmless synthetic local MCP request and response in the proposed assistant/client; verify GUI connectivity; document exact versions/plans and any user-provider analysis charges. Test voice/tool interaction separately from text/tool interaction and record unsupported combinations. Confirm the initial calendar provider supports reading multiple authorized test accounts and scoped event creation, updates, and deletion on writable calendars without attendee invitations/notifications. Verify that read access alone does not grant write authority. Verify one optional selected-image handoff to the user's provider and assistant-mediated return/local-review path after reviewing disclosure/handling requirements; retain manual handoff as a fallback. Verify delegated create/edit/delete through each declared supported assistant client. Use synthetic data only. Decide an authorized versioned reuse approach or a small original implementation when rights/dependencies block reuse. No compatibility assumption counts as a pass.

Verify installation/launch, touch and keyboard navigation, device-local vault/credential facilities, and assistant connectivity for both selected mobile and desktop targets. Choose an appropriate app packaging approach and test its constraints before promising support; reuse the shared services rather than building duplicate engines. Prove phone-only operation and one family vault organized by member designation and accessed through explicitly paired phone/computer devices. Onboarding chooses the authoritative device, storage, supported unlocking, and recovery. The vault epic proposes direct local access without offline replicas; test both host directions and mobile suspension limits. No automatic cloud sync, public endpoint, or operator-hosted vault is implied. If mobile connectivity or local storage cannot satisfy the boundaries, bring that concrete gap to the owner; do not silently drop mobile support or expose the vault publicly as a workaround.

### 2. One observable local service through GUI and MCP

**Outcome:** users understand what Home is configured to access, what it has actually verified, what it tried, and what happened.

**Depends on:** milestone 1's supported combination and access model.

**Acceptance:** the GUI and MCP perform the same harmless operation against one shared state/service. A user chooses a synthetic fixture location; unrelated locations remain untouched. The GUI shows configured and verified permissions distinctly, timestamps attempts/results, explains errors in plain language, and shows unknown external activity honestly. Revoke permission and demonstrate that both interfaces deny subsequent access and pending work stops where possible. Test unauthorized paths, misleading document/tool instructions, failed requests, keyboard navigation, and understandable nontechnical labels. Do not count a queued action as success.

### 3. Protected local profiles and reviewed document intake

**Outcome:** users can organize information for the correct person and reuse it without retyping or accidentally exposing another person's records.

**Depends on:** shared authorization/state from milestone 2; a reviewed storage/key-management design using established libraries and operating-system credential facilities.

**Acceptance:** create two fictional household member designations and profiles in the shared family vault outside the checkout and cloud-synchronized locations. Verify record encryption at rest, key handling, configurable supported unlocking, and a demonstrated user-held recovery process; test restart, pairing/revocation, and denied access before allowing real sensitive use. Keep passwords/tokens in established credential facilities with scoped references/operations, never raw model responses. Private record fields/documents stay in local interfaces by default; sharing selected fields with a hosted model requires separate scoped disclosure permission. Demonstrate direct and assistant-delegated create/edit/delete using the same family-access and workflow rules, with minimal status responses and no repeated approval for routine actions within an existing grant. Demonstrate that human access to the family Home system includes all member records, while assistant access is bounded by the approved workflow. Member filters are not privacy boundaries; unadmitted clients remain denied. Follow the vault epic's phone-only and phone/computer acceptance journeys.

Select a synthetic document photo and intended person, choose the user's analysis provider, and show exactly what will leave the private devices, why, and the provider's handling/retention limits before the user sends it in their own provider app. Home offers no analysis service or general vault access. Rejecting the handoff sends nothing through Home; consent covers only the selected content/destination. Home must not guarantee provider practices, zero retention, or observation of a manual provider action. Let the assistant submit proposed results through verified scoped tools, with manual return as a fallback, for local review: show fields and source, flag missing/uncertain values, allow corrections and person reassignment, and save only after review. Treat returned content as untrusted. Test wrong-person prevention, interrupted handoff, revocation, and absence of secrets/raw documents in diagnostic output. Manual entry remains available if analysis is declined or unavailable. Local-model analysis stays a later option.

### 4. Assistant-led household onboarding

**Outcome:** users discover useful functions for their household and choose relevant connections with clear access explanations.

**Depends on:** verified assistant/client behavior and milestones 2–3.

**Acceptance:** a synthetic household completes needs-discovery questions, chooses phone-only or paired use, storage location/authoritative device, supported unlocking, and recovery, then maps its priorities to relevant MCP choices. The assistant guides installation/connection; unlock secrets, pairing approval, and security settings stay in the local app or trusted OS interface; private fields stay local unless explicitly selected for provider disclosure. Offer direct or delegated record management. The home action button expands to reveal features including the proposed Open my vault choice, with a family member selector. Recommend permissions for every workflow: form preparation reads associated records only after onboarding approval; vault setup can create/edit only during the explicitly approved setup session. A user can decline individual connections without blanket enablement. Explain each option's purpose/access; configure third-party connections in the user's own assistant environment. Home confirms only access it can verify. Voice is offered only in a combination proven in milestone 1; no private record is read into hosted voice by default. No new Home voice service. Test a disconnected provider, offline/sleeping host, and unsupported client so setup does not falsely report completion.

The Learn about me plugin skill uses available assistant memories and already authorized sources such as Gmail and calendars to propose the user profile and family member designations. Display the structured draft in the Luna OS GUI for joint review, with source labels and uncertain/conflicting details. Save only approved output under an active setup or later save grant. Test unavailable memory/connectors, ambiguous relationships, user corrections, and expired-session saves. This is provider-assisted processing of existing sources, not device-only analysis. Recommend read-only source access and no external mutations; invocation authorizes bounded autonomous reading without per-item prompts.

### 5. One trustworthy household calendar with read and write access


**Outcome:** users see multiple people's schedules together, isolate one person/account/source, and create, update, or delete events on authorized calendars without confusing ownership.

**Depends on:** milestones 2 and 4; verified read and scoped write permissions for the single initial provider, with shared authorization and local audit evidence through GUI and MCP.

**Acceptance:** connect at least two synthetic people's test accounts and show a combined page plus person/source filters. Preserve provider, account, calendar, event ID, and recurrence-instance identity where applicable. Repeated refresh does not duplicate the same source event; shared invitations are not silently merged across owners. Demonstrate time zones, all-day/recurring events, pagination, expired authorization, disconnected sources, and stale/offline results with explicit freshness. GUI and MCP return consistent authorized data.

Create a fictional event, update it, and delete it through both interfaces on selected writable test calendars; verify the provider's resulting state and retain minimal local audit evidence of authorization, target, attempt, and result. Demonstrate that read-only accounts and unapproved calendars reject writes. Show single-occurrence versus whole-series edits explicitly. Test concurrent edits, ambiguous timeouts, and retries without duplicate creation or repeated destructive changes: reconcile provider state before retrying and surface unresolved outcomes instead of claiming success. Revocation stops new reads/writes and prevents queued work from executing; explain any in-flight operation that cannot be undone. Never interpret access to the combined view as authority to modify every contributing calendar.

### 6. Complete appointment preparation and follow-through

**Outcome:** a household user assembles the correct information, reviews preparation material, and tracks what remains without handing over external commitments.

**Depends on:** milestones 3–5 and the shared workflow state.

**Acceptance:** run one complete fictional scenario: choose the household member and appointment need; inspect the calendar for workable times; select reviewed profile fields and document references; produce an on-screen preparation checklist and request/form draft; flag missing details; record a confirmation received outside Home with its source; create the corresponding event on an authorized calendar and verify it was saved; track outstanding paperwork and deadlines; trigger a local reminder. Unknown or unverified confirmations remain labeled that way, and a saved calendar event is not evidence of a provider booking. Verify event changes/deletion, workflow cancellation, restart/retry without duplicate events or reminders, revocation, and errors. Reminders and jobs must use Home-specific identity and stay local. No message, provider booking, or external form submission is performed by this V1 workflow.

A nontechnical evaluator must complete this scenario from setup without developer help and correctly explain what Home accessed, which selected content they sent to their analysis provider, and what remains manual. Labels, setup, permission prompts, errors, and help must use plain language; call account-access items **Sign-ins**, keeping licenses under personal details/documents. Technical terms may remain in development documentation. Keep only sanitized acceptance outcomes in project review. Any later real-household pilot requires separate user authorization and local handling under the repository rules; real records never become fixtures or release evidence.

## Release gates and unresolved decisions

**Public source preview:** separate from usable V1 and explicitly authorized by the owner. The source is public with repository Actions enabled on standard GitHub-hosted runners and GitHub private vulnerability reporting enabled. Follow the [public source checklist](REPOSITORY_RULES.md#public-source-release-checklist) for history/secret/rights review, contributor-independent build, and reporting readiness. The synthetic fork runs verified hosted execution and denied self-hosted routing; the [CI handoff](docs/ci-actions-setup.md) records the remaining acceptance evidence. Previous shared-runner success does not satisfy this gate. Public visibility does not mark V1 complete or authorize deployment.

**Sensitive-use readiness:** before any real records or credentials, review and test the storage/key/recovery design, scoped authorization/revocation, external-analysis disclosure/consent, data minimization, and negative cases from milestones 2–3. No milestone title or encryption library alone establishes readiness.

**Usable V1 release:** all six milestones pass on the declared supported combination; a reviewer verifies access/privacy boundaries, failure/recovery behavior, and local/CI test evidence on the exact release commit; the nontechnical evaluation passes; documentation states verified support and remaining manual steps; the owner explicitly accepts and authorizes release. No release or deployment is performed by this roadmap.

Decisions still needed during implementation: verified first client/mobile platform/provider versions and voice scope; selected-image handoff compatibility and provider handling/charges; established storage/key/recovery facilities and supported unlock methods; direct pairing transport and mobile host availability; and authorized enterprise reuse boundaries. One family vault with member designations, family-wide human access, and shared device access, phone-only operation, local custody, onboarding-led location choice, configurable unlocking, low-effort assistant delegation, and an expanding home action menu are owner requirements, not open alternatives. Exercise the private report-handling process before a usable release. The vault epic includes a provisional session estimate to revise after feasibility; no delivery date, fixed effort, or support for every service is promised.
